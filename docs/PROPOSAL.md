# 알약찾기(가칭) — 낱알식별 약 검색 앱 제안서

간호사가 근무 중 휴대폰으로 알약을 빠르게 식별할 수 있게 하는 모바일 앱 제안서입니다.

- 작성일: 2026-09-24
- 상태: 기획(제안) 단계
- 화면 시안: [`docs/prototype/index.html`](prototype/index.html) (가상 데이터로 눌러보는 시안, 브라우저로 열기)

## 1. 사용 장면

- 입원 환자가 가져온 **지참약** 확인. 약봉투 없이 알약만 있는 경우가 많음
- 병실 바닥·침대에서 **발견된 알약** 확인
- 투약 전 약포지 속 약이 **처방과 맞는지** 확인

공통 조건: 한 손엔 약, 장갑 착용, 시간 부족, 통신이 불안정한 곳도 있음.
그래서 **입력은 최소로, 응답은 즉시, 통신 없이도 동작**하는 것이 설계 목표입니다.

## 2. 데이터 소스 (가장 중요한 결정)

### 2.1 선택지 비교

| | A. 약학정보원 웹 바로 열기 | **B. 공공데이터로 자체 검색 (추천)** | C. 약학정보원 데이터 계약 |
|---|---|---|---|
| 방법 | 앱 안 브라우저로 약학정보원 낱알식별 화면을 연다 | 식약처 낱알식별 데이터를 받아 앱 안에 검색 DB를 만든다 | 약학정보원과 계약해 DB를 공급받는다 |
| 입력 편의 | 약학정보원 화면 그대로라 개선이 어려움 | 자유롭게 설계 가능 | 자유롭게 설계 가능 |
| 오프라인 | 불가 | 가능 | 가능 |
| 법적 위험 | 링크만 걸면 낮음. 조건 자동 입력·결과 가공은 이용약관 확인 필요 | 낮음 (이용허락범위 확인, 출처 표시) | 없음 (계약) |
| 비용 | 없음 | 없음 | 협의 필요 |
| 어울리는 단계 | 임시 바로가기 | 개인·병동 파일럿부터 병원 도입까지 | 병원 공식 도입 |

**추천: B로 만들고**, 결과 화면에 "약학정보원에서 보기"(복약정보 등 상세)와 "의약품안전나라에서 보기" 버튼을 둡니다. 병원 공식 도입 단계에서 C를 검토합니다.

### 2.2 약학정보원을 직접 붙이지 않는 이유

- 약학정보원 낱알식별 검색은 웹 화면으로만 제공되고, **공개 API는 확인되지 않았습니다.**
- 화면을 자동으로 긁어오는 방식(스크래핑)은 체계적으로 구축된 데이터베이스를 복제하는 셈이라 **저작권법상 데이터베이스제작자 권리와 이용약관 문제**가 생길 수 있습니다. 사이트 구조가 바뀌면 앱이 바로 멈추는 것도 문제입니다.
- 약학정보원은 병원(예: 삼성서울병원, 성빈센트병원)에 의약품 기본정보와 식별정보 DB를 **계약으로 공급한 사례**가 있습니다. 병원 공식 도입이라면 이 경로가 정석입니다. 근무하는 병원의 약제부나 EMR에 이미 들어와 있는지도 확인해 볼 만합니다.

### 2.3 식약처 「의약품 낱알식별 정보」 API

- 제공처: [공공데이터포털](https://www.data.go.kr/data/15057639/openapi.do). 무료이며 활용신청 후 인증키가 발급됩니다.
- 주소: `https://apis.data.go.kr/1471000/MdcinGrnIdntfcInfoService03/getMdcinGrnIdntfcInfoList03`
- 요청 파라미터: `serviceKey`, `item_name`(제품명), `entp_name`(업체명), `item_seq`(품목일련번호), `pageNo`, `numOfRows`, `type=json`

주요 응답 필드:

| 필드 | 뜻 | 앱에서 쓰는 곳 |
|---|---|---|
| `ITEM_SEQ` | 품목일련번호 | 고유 ID, 의약품안전나라 링크 |
| `ITEM_NAME`, `ITEM_ENG_NAME` | 제품명 | 결과 표시, 이름 검색 |
| `ENTP_NAME` | 업체명 | 결과 표시 |
| `ITEM_IMAGE` | 낱알 사진 URL | 결과 사진 |
| `PRINT_FRONT`, `PRINT_BACK` | 식별표시(각인) 앞/뒤 | 각인 검색 |
| `MARK_CODE_FRONT_ANAL`, `MARK_CODE_BACK_ANAL` | 마크(로고) 설명 앞/뒤 | 마크 검색 |
| `DRUG_SHAPE` | 모양 | 모양 칩 |
| `COLOR_CLASS1`, `COLOR_CLASS2` | 색 앞/뒤 | 색 칩 |
| `LINE_FRONT`, `LINE_BACK` | 분할선 앞/뒤 | 분할선 칩 |
| `FORM_CODE_NAME` | 제형 (필름코팅정, 경질캡슐제 등) | 제형 칩 |
| `LENG_LONG`, `LENG_SHORT`, `THICK` | 크기(mm): 장축, 단축, 두께 | 크기 비교 |
| `CLASS_NAME`, `ETC_OTC_NAME` | 분류명, 전문/일반 | 상세 화면 |
| `CHART` | 성상 (예: 흰색의 원형 필름코팅정) | 상세 화면 |
| `CHANGE_DATE` | 변경일자 | 데이터 갱신 추적 |

그 밖에 `EDI_CODE`(보험코드), `STD_CD`(표준코드), `ITEM_PERMIT_DATE`, `MARK_CODE_FRONT_IMG` 등이 있습니다.

> **중요:** 이 API는 제품명·업체명·품목일련번호로 조회하는 구조라 "원형 + 하양 + 각인 DW" 같은 **조건 검색을 직접 해주지 않습니다.**
> 그래서 전체 목록을 페이지 단위로 한 번에 받아 **앱이 쓸 검색 DB(SQLite 파일)** 를 만듭니다.
> 이 방식은 장점이기도 합니다. 휴대폰 안에서 검색하니 결과가 즉시 나오고, 통신이 끊겨도 동작합니다.

그 밖에 확인할 점:

- 의약품안전나라 상세 링크는 `ITEM_SEQ`로 바로 만들 수 있습니다: `https://nedrug.mfds.go.kr/pbp/CCBBB01/getItemDetail?itemSeq={ITEM_SEQ}`
- 약학정보원 상세 페이지는 자체 코드(`drug_cd`)를 써서 `ITEM_SEQ`로 바로 연결되지 않습니다. 제품명으로 약학정보원 검색 화면을 여는 방식으로 연결하고, 정확한 연결 방법은 개발 단계에서 확인합니다.
- 식별표시가 면제된 약이나 최근 허가·변경된 약은 빠지거나 늦게 반영될 수 있습니다. 결과가 없으면 "데이터에 없을 수 있음"을 안내하고, 화면에 데이터 기준일을 표시합니다.
- 의약품 식별표시는 식약처와 약학정보원이 함께 운영하는 체계([pharm.or.kr](https://www.pharm.or.kr/))로 등록·관리되므로 두 곳의 정보는 같은 출처에서 나온 것으로 보입니다. 그래도 0단계에서 무작위 50개 정도를 약학정보원 결과와 직접 비교해 확인합니다.

## 3. 전체 구조

```mermaid
flowchart LR
    MFDS["식약처 낱알식별 OpenAPI<br/>(공공데이터포털)"] --> GA
    subgraph GH["GitHub"]
        GA["Actions (주 1회)<br/>데이터 수집·정리"] --> DB["pills.sqlite<br/>(검색용 데이터 파일)"]
    end
    DB -->|새 버전이 있으면 내려받기| APP["휴대폰 앱 (Expo)<br/>오프라인 검색"]
    APP -->|사진 (선택)| SRV["서버 함수<br/>(Cloudflare Workers)"]
    SRV -->|이미지 분석 요청| AI["Claude API"]
    AI -->|"JSON: 각인·색·모양"| SRV
    SRV --> APP
    APP -->|상세 보기 링크| EXT["약학정보원 / 의약품안전나라"]
```

- **데이터 흐름**: GitHub Actions가 매주 식약처 API에서 전체 목록을 받아 정리(각인 표기 통일 등)한 뒤 `pills.sqlite`를 만듭니다. 앱은 시작할 때 새 버전이 있으면 내려받고, 없으면 가지고 있는 데이터로 동작합니다.
- **사진 분석**: 1차는 휴대폰 안에서 처리합니다(무료, 오프라인). 서버 AI 분석은 선택 기능입니다. 서버는 API 키 보관과 중계만 하고 사진을 저장하지 않습니다.
- **약 사진**: `ITEM_IMAGE` 주소에서 필요할 때 불러와 휴대폰에 캐시합니다. 전체 사진을 앱에 넣기에는 용량이 너무 큽니다.

## 4. 기술 스택 (추천)

| 영역 | 추천 | 이유 |
|---|---|---|
| 앱 | React Native + Expo (TypeScript) | iOS·안드로이드를 한 번에 개발. Mac 없이 클라우드 빌드(EAS Build), 간단한 수정은 스토어 심사 없이 배포(EAS Update). 웹 버전도 만들 수 있어 설치 없이 파일럿 가능 |
| 휴대폰 안 DB | SQLite (`expo-sqlite`) | 수만 건도 즉시 검색, 오프라인 |
| 카메라 | `react-native-vision-camera` | 초점·노출 제어, 실시간 프레임 처리 |
| 휴대폰 안 글자 인식(OCR) | Google ML Kit 텍스트 인식 v2(안드로이드), Apple Vision(iOS) | 무료, 오프라인, 영문·숫자·한글 인식 |
| 서버 | Cloudflare Workers | 무료 구간으로 시작 가능. API 키 보관, AI 분석 중계, 데이터 파일 제공 |
| AI 사진 분석 | Claude API (이미지 입력 + 정해진 JSON 형식 출력) | 흐린 음각 각인, 색, 모양을 구조화된 값으로 추출 |
| 코드·자동화 | GitHub (Issues, Projects, Actions, Secrets, Releases) | 7장 참고 |

- Flutter도 좋은 대안입니다. 이미 Dart/Flutter에 익숙하다면 Flutter를 쓰세요. 중요한 것은 프레임워크보다 **데이터와 검색 로직**입니다.
- ML Kit와 Vision Camera는 Expo Go 앱으로는 실행되지 않고 "개발 빌드(development build)"가 필요합니다.
- 웹 버전에서는 휴대폰 안 OCR을 쓸 수 없으므로 조건 검색과 서버 AI 분석만 제공합니다.

## 5. 쉬운 입력 설계 (간호사용)

```
┌───────────────────────────────────┐
│ 알약찾기             [조건 지우기] │
│                                   │
│ 각인 (앞·뒤 상관없이)             │
│ ┌───────────────────────────────┐ │
│ │ VX 10                         │ │ ← 누르면 영문·숫자 전용 키패드
│ └───────────────────────────────┘ │
│ 모양  [●원형] [⬭타원] [▭장방] ... │ ← 그림 버튼, 여러 개 선택 가능
│ 색    [○하양] [●노랑] [●주황] ... │ ← 색 견본 버튼
│ 제형  [정제] [경질캡슐] [연질캡슐] │
│ 분할선 [없음] [ - ] [ + ]          │
│                                   │
│ [카메라]  [   후보 3개 보기   ]    │ ← 엄지가 닿는 아래쪽
└───────────────────────────────────┘
```

- **아는 것만 누르기**: 모든 조건은 선택 사항입니다. 누르지 않으면 '모름'으로 처리합니다.
- **누를 때마다 후보 수 표시**: "후보 12개"처럼 바로 보여주고, 몇 개 안 남으면 곧바로 결과를 봅니다.
- **각인 전용 입력**: 영문 대문자·숫자만 입력해 한/영 전환이 필요 없습니다. 띄어쓰기·하이픈은 무시하고, 앞/뒤 어느 면의 글자든 찾습니다. 헷갈리는 글자(O↔0, I·L↔1, S↔5, B↔8, Z↔2)도 함께 찾습니다.
- **드롭다운 대신 큰 칩**: 모양은 그림, 색은 색 견본으로 보여줍니다. 두 가지 색 캡슐은 두 색을 모두 선택합니다.
- **막다른 길 없애기**: 결과가 0개면 "색 조건을 빼면 3개"처럼 어떤 조건을 풀면 되는지 알려줍니다.
- **한 손 조작**: 주요 버튼은 화면 아래쪽에 두고, 터치 영역은 48dp 이상으로 만들어 장갑을 낀 손도 고려합니다.
- **사진 중심 결과**: 앞/뒤 사진을 크게, 크기(mm), 분할선, 업체, 전문/일반을 함께 보여줍니다. 비슷한 후보 2~3개를 나란히 비교할 수 있게 합니다.
- **빨리 열기**: 로그인 없이 앱을 열면 바로 검색 화면이 나옵니다. 홈 화면 바로가기("카메라로 찾기")도 둡니다.
- **오프라인**: 병동, 지하, 엘리베이터에서도 검색됩니다.
- **야간 근무 배려**: 다크 모드와 글자 크기 조절을 지원합니다.
- **자주 쓰는 약 우선**: 최근 검색과 즐겨찾기를 두고, 선택 기능으로 우리 병원 원내 약을 먼저 보여줍니다.

## 6. 카메라 검색 설계

### 6.1 현실적인 목표

- 알약은 크기·색·모양·제형이 같고 각인만 다른 경우가 많아서, 사진만으로 제품을 맞히기는 어렵습니다.
- 식약처 연구용역 보고서 요약에 따르면 알약 이미지 인식률은 실험실 테스트에서 95% 이상이었지만, 시범(실사용) 테스트에서는 평균 15% 정도였습니다. ([ScienceON 보고서](https://scienceon.kisti.re.kr/srch/selectPORSrchReport.do?cn=TRKO202300003907))
- 그래서 목표를 이렇게 잡습니다: **사진 → 검색 조건 자동 입력 → 후보 목록 → 사람이 사진을 비교해 확정.** "이 약은 ○○입니다"라고 단정하지 않습니다.

### 6.2 흐름

1. **촬영 가이드**: 단색 바탕(밝은 약은 어두운 바탕), 원 안에 알약 1개, 그림자 없이. 앞면을 찍고, 필요하면 뒤집어서 뒷면을 찍습니다.
2. **분석**
   - ① **휴대폰 안 분석** (무료, 오프라인, 빠름): 배경에서 알약을 분리하고, 대표 색을 16가지 색 분류 중 가장 가까운 색으로 정하고, 윤곽선으로 모양을 추정하고, 글자 인식(OCR)으로 각인을 읽습니다. 인쇄된 글자는 잘 읽지만 음각·양각(새긴 글자)은 약합니다.
   - ② **서버 AI 분석** (선택): Claude API에 사진을 보내 각인 앞/뒤, 색, 모양, 제형, 분할선을 정해진 JSON 형식으로 받습니다. **제품명은 추측하지 않고 보이는 특징만** 뽑게 해서 지어낸 답이 나올 위험을 줄입니다. 값은 앱의 분류 목록 안에서만 고르게 형식을 제한합니다.
3. **조건 자동 채움**: 자동으로 채운 칸은 노란색으로 표시하고, 틀린 칸은 눌러서 고칩니다. 그다음 휴대폰 안 DB를 검색하고, 후보 사진과 비교해 확정합니다.

### 6.3 AI 분석 결과 예시

```json
{
  "imprint_front": "VX 1O",
  "imprint_back": null,
  "imprint_style": "음각",
  "colors": ["하양"],
  "shape": "원형",
  "dosage_form": "정제",
  "score_line": "없음",
  "confidence": { "imprint": "낮음", "color": "높음", "shape": "높음" },
  "retake_advice": "각인이 흐립니다. 옆에서 빛을 비추고 다시 찍어 주세요."
}
```

위 예시처럼 `O`와 `0`을 헷갈려도 검색 단계의 유사 글자 보정으로 후보에 포함됩니다.

### 6.4 비용과 보안

- **비용(추정)**: 사진을 긴 변 1,280px 정도로 줄여 보내면 사진 1장이 입력 토큰 약 1,200~1,600개입니다. Claude 상위 모델 기준으로 1회 분석에 약 2~5센트(약 30~70원)로 추정합니다. 실제 비용은 API 응답의 사용량 기록으로 확인해야 합니다.
  - 휴대폰 안 분석 결과가 충분하면 서버 호출을 건너뛰어 비용을 줄입니다.
  - 더 저렴한 모델로 바꿀지는 정확도를 비교한 뒤 결정합니다.
- **API 키는 앱에 넣지 않습니다.** 앱 파일은 뜯어볼 수 있기 때문입니다. 키는 서버 함수에만 두고, 앱은 서버를 호출합니다. 서버에는 호출량 제한과 간단한 인증을 둡니다.
- **환자 정보 보호**: 환자 이름·등록번호가 적힌 약봉투나 팔찌가 찍히지 않도록 안내하고, 알약 부분만 잘라서 보냅니다. 서버는 사진을 저장하지 않습니다.
- **병원 보안 정책**: 외부 AI로 사진을 보내는 것이 허용되지 않으면 ① 휴대폰 안 분석만 쓰는 모드로 운영합니다.

### 6.5 장기 과제: 자체 AI 모델

- AI Hub [「경구약제 이미지 데이터」](https://www.aihub.or.kr/aihubdata/data/view.do?currMenu=115&topMenu=100&aihubDataSe=data&dataSetSn=576): 국내 유통 경구약 5,000종(전문 3,000종, 일반 2,000종)을 여러 각도·조명·배경에서 찍은 이미지. 단일 알약과 3~4개 조합 이미지, 위치(바운딩박스) 라벨 포함.
- 식약처 [「인공지능 개발을 위한 알약 이미지 데이터」](https://www.data.go.kr/data/15112582/fileData.do) (공공데이터포털).
- 쓰임새: 한 장에 여러 알약이 있을 때 하나씩 찾아내기(검출), 후보 순위 다시 매기기. 데이터 이용 조건(신청 절차, 상업적 이용 범위)은 먼저 확인해야 합니다.

## 7. GitHub로 진행하는 방법

### 7.1 저장소 구조 (예정)

```
Drug/
├─ apps/mobile/          앱 (Expo)
├─ server/               서버 함수 (사진 분석 중계, 데이터 파일 제공)
├─ data/                 낱알식별 데이터 수집·정리 스크립트, 검색 로직 테스트
├─ docs/                 제안서, 화면 시안
└─ .github/workflows/    CI, 데이터 주간 갱신, 앱 빌드
```

### 7.2 GitHub 기능 활용

- **Issues + Projects**: 8장 로드맵 항목을 이슈로 만들고 칸반 보드로 관리합니다.
- **Actions**
  - `ci.yml`: PR마다 타입 검사와 테스트를 돌립니다. 특히 검색 로직(각인 정규화, 유사 글자) 테스트가 중요합니다.
  - `data-refresh.yml`: 매주 식약처 API에서 전체 목록을 받아 `pills.sqlite`를 만들고 배포합니다.
  - `mobile-build.yml`: 버전 태그를 달면 EAS로 앱을 빌드합니다.
- **Secrets**: `DATA_GO_KR_SERVICE_KEY`, `ANTHROPIC_API_KEY`(서버 배포용), `EXPO_TOKEN`. 키는 절대 코드에 커밋하지 않습니다.
- **공개 여부**: 병원 내부용이면 비공개 저장소를 추천합니다.
- **Claude Code 활용**: 이슈 단위로 구현을 요청하고 PR → 리뷰 → 병합 흐름으로 진행할 수 있습니다.

## 9. 꼭 챙길 것

- **저작권·이용조건**: 약학정보원 콘텐츠는 복제·재배포하지 않고 링크로 연결합니다. 공공데이터는 이용허락범위를 확인하고 앱에 출처("식품의약품안전처 의약품 낱알식별 정보")를 표시합니다.
- **환자 안전**: 앱 결과는 참고용입니다. 최종 확인은 처방 내역, 약제부 확인과 함께 합니다. 사진만으로 단정하는 화면을 만들지 않고, 데이터 기준일을 표시합니다.
- **개인정보·보안**: 환자 정보와 사진을 저장하지 않습니다. 외부 전송은 병원 승인 후에만 합니다.
- **의료기기 해당 여부**: 정보 조회용 참고 도구로 설계하고 진단·치료 목적의 표현을 쓰지 않습니다. 병원 공식 도입이나 상용화 전에는 식약처의 의료기기(소프트웨어) 해당 여부 판단 기준을 확인합니다.
- **앱 스토어 심사**: 의료 관련 앱은 심사를 더 엄격하게 받을 수 있으니 데이터 출처와 면책 문구를 분명히 적습니다.
